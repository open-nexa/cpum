# CPU Manager v0.2.0

> Download links for every release live on the
> [download page](https://open-nexa.github.io/cpum/), which reads them from the
> GitHub releases API. The filenames below are for reference only — do not copy a
> link from this file, it can drift from what was actually published.

**v0.2.0 is a "people can actually find and install it" release**, plus the
performance pass that came out of profiling the metrics pipeline. The feature set
is the one 0.1.0 shipped; what changed is how reachable it is, how honest the
numbers in it are, and how much work the app does per second to show you the
same table.

- **Tag:** `v0.2.0`
- **Released:** 2026-10-08
- **Platforms:** Windows x64 / ARM64 (Windows 10 and later)

## Highlights

### Reaching people

- **A download page** at
  [open-nexa.github.io/cpum](https://open-nexa.github.io/cpum/), published from
  `docs/releases/` by `.github/workflows/pages.yml`. Every link is read from the
  releases API and classified in code — no filename is ever built from a template,
  so a renamed artifact cannot turn into a 404. There is a `localStorage` cache
  and a committed snapshot for when the API is rate-limited or unreachable.
- **An `Install` section in both READMEs**, covering both architectures, how to
  verify the download with `SHA256SUMS.txt`, and the SmartScreen warning an
  unsigned installer produces. Until now neither README said where the installer
  comes from.
- **Screenshots in both READMEs** — process list in flat and tree view, the rule
  manager, the ProBalance panel — plus `screenshots/README.md` recording how they
  were captured so the next set is consistent.
- **`docs/ROADMAP.md`**: what is solid, what is not, the next four phases, and a
  non-goals section with the reason for each one. It is written to be argued
  with.
- **Contributing surface**: `CONTRIBUTING.md`, `SECURITY.md`,
  `CODE_OF_CONDUCT.md`, issue and PR templates, Dependabot, and CodeQL +
  gitleaks secret scanning, so a leaked key fails the build rather than the
  release.

### Performance

Profiled end to end and fixed where the measurement said so, not where it felt
slow. Full write-up in `docs/PERFORMANCE-FIX-PLAN.md`.

- **The process table is virtual-scrolled.** `v-data-table` ran with
  `items-per-page="-1"`, so every row was live in the DOM and every metrics tick
  patched all ~390 of them while only ~20 were on screen. The new
  `src/components/ProcessTable.vue` renders the viewport plus a small overscan —
  390 rows of input produce 22 rendered rows — and owns its own sorting. Columns,
  tree indentation, the right-click menu, priority colours and the per-CCD
  affinity swatches are unchanged.
- **Applying a rule no longer rewrites what is already correct.** The service used
  to rewrite affinity and all three priority classes for every matching process
  every five seconds, and each write makes the kernel re-evaluate thread placement
  for every thread in the process. It now reads the current state first and skips
  the write when it already matches. A process whose state cannot be read is still
  written every time, so this can only ever cost less — never stop a rule from
  being enforced. `cpum_service --apply-once --force` bypasses the comparison.
- **Fewer syscalls per round.** The network counters reuse the process handle the
  sampler already holds instead of opening a second one (which also asked for
  `PROCESS_QUERY_INFORMATION` more often than it was granted, so the network
  column now populates for *more* processes, not just faster). The per-process
  walk is single-threaded below 600 processes, where the measured cost of
  spawning threads (11.3 ms with 8 threads) exceeded the work itself (10.1 ms).
  The resolved exe path and the three priority classes are cached, keyed on PID
  *and* process creation time so a recycled PID cannot inherit another process's
  values.
- **One front-end timer instead of two.** The ProBalance panel no longer runs its
  own 2 s poll; `App.vue` drives it from the 1 s tick it already ran, so the
  per-core usage read and the panel refresh stop landing in the same frame.

### Correctness

- **Four CSS rules that never applied.** `App.vue` had a non-scoped `<style>`
  block using `:deep(.v-main)`, `:deep(.v-container)` and two `:deep(.v-data-table
  …)` rules. Vue only rewrites `:deep()` inside a *scoped* block; elsewhere it is
  emitted verbatim and matches nothing. The viewport height constraint and the
  fixed-column / ellipsis rules for the process table had therefore been inert
  since they were written — invisible under Vite 6's esbuild, and reported by
  Vite 8's lightningcss. Layout rules are now plain global selectors; the two
  table rules are gone because the virtual-scrolled table implements fixed
  columns and ellipsis itself.
- **Tree mode kept its children.** Rows were sorted globally, so a child with a
  higher CPU figure than its parent moved away from it while keeping the parent's
  indentation — expanding the parent no longer revealed its subtree. Sibling
  groups are now sorted within themselves.
- **Narrow windows can reach the right-hand columns.** The columns have minimum
  widths and the table body scrolls horizontally with the header following.
- **"Applied to N processes" no longer under-reports.** When the elevated service
  did the work instead of the GUI's own pass, processes it found already correct
  were returned as *skipped* rather than writes and vanished from the count.
  `ApplyReport` now carries them and both passes feed one de-duplicating set.
- **`get_process_group_masks` could half-read a process.** A process's affinity is
  the union over its threads, so a mask built from some of them can equal a
  rule's masks while the unobserved threads run elsewhere — which made the
  idempotent apply skip a write that was still needed. The read is now
  all-or-nothing: any unreadable thread, or a thread on an unknown processor
  group, returns `None` and the caller writes.
- **`(0, 0)` is not "unconstrained".** `affinity_matches` read a zero affinity
  pair as no constraint and could skip a soft rule on the strength of a read that
  never happened. Windows never reports a mask of 0, so zero now counts as
  unknown and takes the write path.
- **The 2 s priority cache was keyed on PID alone**, so a recycled PID could be
  served its predecessor's priority classes until the next refresh — `prune_caches`
  only drops PIDs that have *disappeared*, and a recycled PID has not. The entry
  now stores the creation time, like the exe-path cache already did.
- **The CI NSIS bundle step could not fail for a real reason.** It passed its
  updater override as inline JSON escaped with backslashes — correct for bash, not
  for PowerShell, which is the default shell on `windows-latest`; the CLI received
  literal backslashes and rejected the value. The override is now a file
  (`src-tauri/tauri.no-updater.conf.json`), so no shell is involved.

### Dependencies

One branch instead of sixteen dependabot pull requests: Vite 8.3,
`@vitejs/plugin-vue` 6.0, `vue-tsc` 3.3, Vuetify 4.2, `sass-embedded` 1.105 and
TypeScript 6.0 on the front end; `tauri` 2.12, `tauri-build` 2.7,
`tauri-plugin-opener` 2.7, `tauri-plugin-updater` 2.13, `uuid` 1.27 and
`windows-service` 0.8 on the Rust side; the GitHub Actions group bumped across all
four workflows.

- **TypeScript stops at 6.0, not 7.0.** 7.0 is the native (Go) compiler and its
  `exports` map has no `./lib/tsc`, which `vue-tsc` resolves; it fails with
  `ERR_PACKAGE_PATH_NOT_EXPORTED`.
- **The Rust and JavaScript halves of each Tauri package are pinned to the same
  version.** `tauri build` refuses to bundle when they differ on major/minor.
- Security: `vue` 3.5.41 → 3.5.43 (`@vue/server-renderer` XSS,
  GHSA-g2v6-rqmx-r4w6), `source-map-js` 1.2.1 → 1.2.2 (event-loop DoS,
  GHSA-68fv-2mgg-jv7q), and `rustls` 0.23.45 (RUSTSEC-2026-0285).
- The two third-party actions in `release.yml` are pinned to commit hashes rather
  than tags, which CodeQL's `actions` analysis requires.

## Upgrading from 0.1.x

**Read this part before replacing your installation.**

- **The bundle identifier is now `com.open-nexa.cpum`**, so the data directory
  moved from `%APPDATA%\com.eason.cpum` to `%APPDATA%\com.open-nexa.cpum`.
  `affinity_rules.json` is migrated automatically on first start. Installers built
  before the identifier change **cannot be upgraded in place** — uninstall the old
  version first, then install 0.2.0. Your rules move with you.
- **The updater endpoint now points at `open-nexa/cpum`.** Installations of 0.1.1
  and older check `yixinin/cpum` and will not see this release, so upgrade to
  0.2.0 by hand once; every later release arrives through the in-app updater.
- The 5-second service poll, the 1-second metrics cadence, the rule schema and
  the ProBalance journal format are all unchanged. Existing rules keep working
  without editing.

## Install

| Architecture | Installer |
| ------------ | --------- |
| x64 | `CPU-Manager_v0.2.0_windows-x64-setup.exe` |
| ARM64 | `CPU-Manager_v0.2.0_windows-arm64-setup.exe` |

Also published: the matching `.sig` signatures, the updater archives
(`.nsis.zip` + `.sig`), `latest.json`, and `SHA256SUMS.txt`.

The installer is a **per-user** NSIS package that installs into `%LOCALAPPDATA%`
and does not prompt for UAC. The app itself always runs un-elevated; only
installing or removing the Windows service asks for administrator rights, and
that is a single prompt for that action alone.

### Requirements

- Windows 10 or later (x64 or ARM64); WebView2 Runtime, which ships with current
  Windows installations.
- Windows 10 1803 or later for the **soft** rule mode (CPU Sets).
- Windows 11 24H2 or later for per-process **network I/O counters**; older
  versions report them as zero.
- Administrator rights **only** for service install / uninstall / start / stop.

### Verify your download

```powershell
Get-FileHash .\CPU-Manager_v0.2.0_windows-x64-setup.exe -Algorithm SHA256
```

Compare the hash with the matching line in `SHA256SUMS.txt`.

## Known limitations

- **The installers are still unsigned**, so SmartScreen warns on first run. Code
  signing through SignPath Foundation is the remaining item in Phase 0 of the
  roadmap; this costs more downloads than any missing feature does.
- **ProBalance is still experimental** and is labelled *Unstable* in the UI, in
  the toolbar tooltip and as a chip next to the panel title. The heuristic works;
  the threshold defaults are guesses, and there is no journal analysis tooling yet.
  It loses the label on evidence, not on optimism.
- **ARM64 is built but not validated.** CI produces the installer from the same
  source, but topology detection — CCD grouping, hybrid P/E-core classification —
  has only ever been exercised on x64. Validating it is Phase 1.
- **The rule engine polls** every five seconds rather than subscribing to
  process-creation events, so a process that starts, runs and exits between two
  ticks is never pinned.
- Network I/O counters need Windows 11 24H2+ and read zero on older builds.
- Saving a rule does not apply it until you use **Apply Rules** or the service
  scans a matching process.
- PPL processes (and some anti-cheat / antivirus processes) cannot be modified at
  any privilege level; the error is surfaced as-is rather than worked around.
- A handful of success messages returned by the backend are not yet localized, so
  an English sentence can occasionally appear in the Chinese UI.

## Security and reporting

The desktop app runs un-elevated; only service management elevates, and the GUI
reaches processes it cannot open through the service over a named pipe guarded by
a per-user token, rather than raising a UAC prompt. See
[SECURITY.md](https://github.com/open-nexa/cpum/blob/main/SECURITY.md) for the
privilege boundary and for how to report a vulnerability privately.
