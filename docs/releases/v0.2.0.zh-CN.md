# CPU Manager v0.2.0

> 每个版本的下载链接都在[下载页](https://open-nexa.github.io/cpum/)，链接由
> GitHub releases API 读取。下面出现的文件名仅供对照，不要直接复制这里的链接——
> 它可能与实际发布的产物不一致。

**v0.2.0 是一次"让别人找得到、装得上"的发布**，外加一次针对指标采集链路的
性能优化。功能集合与 0.1.0 相同，变化在于可达性、界面里数字的可信度，以及
显示同一张进程表时每秒要做多少工作。

- **Tag：** `v0.2.0`
- **发布：** 2026-10-08
- **平台：** Windows x64 / ARM64（Windows 10 及以后）

### 性能

这次是端到端实测后按数据修的，不是按感觉修的。完整记录见
`docs/PERFORMANCE-FIX-PLAN.md`。

- **进程表改为虚拟滚动。** `v-data-table` 之前是 `items-per-page="-1"`，每一行都
  真实存在于 DOM 中，每秒一次指标刷新会去更新全部约 390 行，而屏幕上只看得见约
  20 行。新的 `src/components/ProcessTable.vue` 只渲染视口加少量缓冲——390 行输入
  最终只产出 22 个渲染行——排序也收进组件内部。列结构、树形缩进、右键菜单、优先级
  配色和按 CCD 的亲和性色块都保持不变。
- **应用规则不再重写已经正确的状态。** 服务此前每 5 秒会对每个命中进程重写亲和性
  与三种优先级，而每次写入都会让内核重新评估该进程所有线程的放置位置。现在先读
  当前状态，已经符合规则就跳过写入。状态读不到的进程仍然每次都写，所以这个改动
  只可能更省，绝不会让规则失效。`cpum_service --apply-once --force` 可绕过比较
  强制写入。
- **每轮系统调用更少。** 网络计数器复用采样器已经持有的进程句柄，而不是再开一个
  （后者还更常申请 `PROCESS_QUERY_INFORMATION` 而被拒绝，因此网络列现在**填得更
  全**，不只是更快）。进程遍历在进程数低于 600 时单线程执行——实测 8 线程 11.3 ms
  vs 单线程 10.1 ms，线程开销高于工作本身。可执行文件路径与三种优先级类都做了缓存，
  键为 PID **加**进程创建时间，避免被复用的 PID 继承前任进程的值。
- **前端定时器从两个减为一个。** ProBalance 面板不再自己跑 2 秒轮询，改由
  `App.vue` 已经存在的 1 秒 tick 驱动，于是每核占用读取与面板刷新不再落在同一帧。

### 正确性

- **四条从未生效的 CSS 规则。** `App.vue` 有一个非 scoped 的 `<style>` 块，里面用了
  `:deep(.v-main)`、`:deep(.v-container)` 和两条 `:deep(.v-data-table …)`。Vue 只在
  *scoped* 块内重写 `:deep()`，其他地方原样输出，什么都匹配不到。也就是说主布局的
  视口高度约束、以及进程表的固定列与省略号规则，从写下来那天起就是死代码——在
  Vite 6 的 esbuild 下悄无声息，直到 Vite 8 的 lightningcss 把它报了出来。布局规则
  现在改为普通的全局选择器；两条表格规则直接删除，因为虚拟滚动的表格自己实现了固定
  列宽与省略。
- **树形视图的孩子不再走丢。** 之前按全局排序，子进程的 CPU 数值一旦高于父进程就会
  离开父节点，却仍保留父节点的缩进——展开父节点反而看不到自己的子树。现在排序
  限制在各自的兄弟分组内进行。
- **窄窗口也能看到右侧列。** 各列有了最小宽度，表体可横向滚动，表头跟随。
- **「已应用到 N 个进程」不再少报。** 当由提权的服务而非 GUI 自身完成时，服务发现
  已经正确的进程会作为 *skipped* 而不是写入返回，于是从计数里消失。`ApplyReport`
  现在携带这些 PID，两趟处理汇入同一个去重集合。
- **`get_process_group_masks` 可能只读到进程的一半。** 进程亲和性是其所有线程的并集，
  用其中一部分线程算出的掩码可能恰好等于规则的掩码，而未被观察的线程却跑在别处——
  这会让幂等应用跳过一笔仍然必要的写入。现在读取改为全有或全无：任一线程打不开，
  或线程报告了未知处理器组，一律返回 `None`，由调用方执行写入。
- **`(0, 0)` 不等于「无约束」。** `affinity_matches` 会把亲和性读数为零的配对当作没有
  约束，从而可能基于一次根本没有发生的读取跳过一条软规则。Windows 从不报告掩码 0，
  所以零值现在算作未知，走写入路径。
- **2 秒优先级缓存过去只以 PID 为键**，被复用的 PID 在下一轮刷新之前可能拿到前任的
  优先级——`prune_caches` 只丢弃已经消失的 PID，而被复用的 PID 并没有消失。现在条目
  记录创建时间，与早已这么做的 exe 路径缓存一致。
- **CI 的 NSIS 打包步骤过去无法因真实原因失败。** 它把 updater 覆盖项以反斜杠转义的
  内联 JSON 传入——这对 bash 是对的，但对 `windows-latest` 的默认 shell PowerShell
  不对，CLI 收到的是字面反斜杠并直接拒绝。现在该覆盖项是一个文件
  （`src-tauri/tauri.no-updater.conf.json`），不经过任何 shell。

### 依赖

一次分支合并，替代十六个 dependabot PR：前端升到 Vite 8.3、
`@vitejs/plugin-vue` 6.0、`vue-tsc` 3.3、Vuetify 4.2、`sass-embedded` 1.105 与
TypeScript 6.0；Rust 侧升到 `tauri` 2.12、`tauri-build` 2.7、
`tauri-plugin-opener` 2.7、`tauri-plugin-updater` 2.13、`uuid` 1.27 与
`windows-service` 0.8；四个工作流的 GitHub Actions 统一提升。

- **TypeScript 停在 6.0，不是 7.0。** 7.0 是原生（Go）编译器，其 `exports` 映射没有
  `./lib/tsc`，而 `vue-tsc` 需要的正是这个入口，会以 `ERR_PACKAGE_PATH_NOT_EXPORTED`
  失败。
- **每个 Tauri 包的 Rust 与 JavaScript 两半锁定到同一版本**——`tauri build` 在两者
  主次版本不一致时拒绝打包。
- 安全更新：`vue` 3.5.41 → 3.5.43（`@vue/server-renderer` XSS，
  GHSA-g2v6-rqmx-r4w6）、`source-map-js` 1.2.1 → 1.2.2（事件循环 DoS，
  GHSA-68fv-2mgg-jv7q）、`rustls` 0.23.45（RUSTSEC-2026-0285）。
- `release.yml` 中的两个第三方 Action 已从 tag 改为锁定 commit hash，CodeQL 的
  `actions` 分析要求如此。

## 从 0.1.x 升级

**替换安装前请先读这一节。**

- **捆绑标识符现为 `com.open-nexa.cpum`**，数据目录因此从
  `%APPDATA%\com.eason.cpum` 迁到 `%APPDATA%\com.open-nexa.cpum`。
  `affinity_rules.json` 会在首次启动时自动迁移。标识符变更之前构建的安装包**无法原地
  升级**——请先卸载旧版本，再安装 0.2.0。规则会随迁移一起带过去。
- **更新源现在指向 `open-nexa/cpum`。** 0.1.1 及更早版本检查的是 `yixinin/cpum`，
  不会看到本次发布，所以请手动升级一次到 0.2.0；之后的版本都可以通过应用内更新器
  获取。
- 5 秒服务轮询、1 秒指标节奏、规则 schema 与 ProBalance 日志格式均未改变。既有规则
  无需修改即可继续工作。

## 安装

| 架构 | 安装包 |
| ---- | ------ |
| x64 | `CPU-Manager_v0.2.0_windows-x64-setup.exe` |
| ARM64 | `CPU-Manager_v0.2.0_windows-arm64-setup.exe` |

同时发布：对应的 `.sig` 签名、updater 归档（`.nsis.zip` + `.sig`）、`latest.json`
以及 `SHA256SUMS.txt`。

安装包是**按用户**的 NSIS 包，安装到 `%LOCALAPPDATA%`，不会弹出 UAC。应用本身始终
以非提权身份运行；只有安装或卸载 Windows 服务才会请求管理员权限，且仅为该操作弹出
一次。

### 环境要求

- Windows 10 及以后（x64 或 ARM64）；WebView2 运行时，当前 Windows 已自带。
- **软**规则模式（CPU Sets）需要 Windows 10 1803 及以后。
- 按进程的**网络 I/O 计数器**需要 Windows 11 24H2 及以后；更早版本显示为零。
- 管理员权限**仅**用于服务的安装 / 卸载 / 启动 / 停止。

### 校验下载

```powershell
Get-FileHash .\CPU-Manager_v0.2.0_windows-x64-setup.exe -Algorithm SHA256
```

与 `SHA256SUMS.txt` 中对应的一行比较。

## 已知限制

- **安装包仍未签名**，首次运行会触发 SmartScreen 提示。通过 SignPath Foundation
  代码签名是路线图 Phase 0 剩下的唯一一项；它造成的下载流失比任何缺失功能都多。
- **ProBalance 仍属实验特性**，界面上明确标注为 **Unstable**——工具栏提示与面板标题
  旁的 chip 都是如此。启发式本身可用，但阈值默认值是拍脑袋定的，日志也还没有配套的
  分析工具。它凭证据摘掉这个标签，而不是凭乐观。
- **ARM64 构建了但没有验证过。** CI 用同一份源码产出安装包，但拓扑检测（CCD 分组、
  混合架构 P 核 / E 核 分类）只在 x64 上跑过。验证它是 Phase 1 的内容。
- **规则引擎靠轮询**，每 5 秒一次，而不是订阅进程创建事件，因此某个在两次 tick 之间
  启动、运行并退出的进程不会被固定。
- 网络 I/O 计数器需要 Windows 11 24H2+，在更早版本上读数为零。
- 保存规则不会立即生效，需要点 **Apply Rules**，或等服务扫描到匹配的进程。
- PPL 进程（以及部分反作弊 / 杀毒进程）在任何权限级别下都无法修改；应用会原样呈现
  该错误，而不是假装绕过去。
- 后端返回的少数成功提示尚未本地化，中文界面里偶尔会出现英文句子。

## 安全与反馈

桌面应用以非提权身份运行；只有服务管理会提权，GUI 需要访问打不开的进程时，是通过
带用户级令牌守护的命名管道交给服务完成，而不是弹 UAC。权限边界与私下报告漏洞的
方式见 [SECURITY.md](https://github.com/open-nexa/cpum/blob/main/SECURITY.md)。
